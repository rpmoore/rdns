# Code Review: Section 04 - DNSSEC Entry Wiring and CD-Bit Gating

Overall the entry-construction wiring, TTL capping, serve-stale Bogus-exclusion, and the mixed-state-chain/CD-bit test coverage match the plan reasonably well, and the deliberate main.rs non-wiring is correctly explained and out of scope per the task framing. But there's one high-severity architectural problem baked into the mechanism itself, plus several smaller gaps.

**HIGH — validation is NOT actually off the client's critical path, contradicting its own doc comment.** `validate_for_store` (src/resolver/mod.rs:6207-6244) is documented as running "after the triggering response has already been decoded and is no longer on that request's critical path for reply latency" (comment at 6220-6224), but that's false as implemented. It's called with `.await` at src/resolver/mod.rs:5806-5809 directly inside `prepare_backend_result`, which is invoked synchronously from `resolve_coalesced_leader` (src/resolver/mod.rs:5093-5106) — the `(decision, response_bytes)` it returns flows straight into `finish_uniform`/`finish` (6394-6415), i.e. the actual reply sent to the querying client. So a cache-miss client is blocked on the full DS/DNSKEY chase before getting any answer at all. Worse, this chase's deadline (`self.dnssec_validation_deadline`, wired in main.rs:172 to `config.per_query_deadline`, default 2s) is a *second, independent* deadline window stacked on top of the resolve's own `query_deadline` used inside `resolve_backend` (src/resolver/mod.rs:8397) — there's no shared/combined budget, so worst-case client-facing latency roughly doubles once trust anchors are configured. It's currently inert only because `main.rs` never calls `with_trust_anchors` (so `self.trust_anchors` stays `None` and `validate_for_store` short-circuits at line 6226-6228 before ever awaiting anything) — but per the new main.rs comment, section-05 is described as flipping this on by default, at which point this latency bomb goes live with no async/background decoupling to prevent it. Compare with `process_refresh_job`'s call site (~4064), which correctly does this validation from an already-background task — the primary client-request path does not get the same treatment, and it needs to (e.g. spawn the DS/DNSKEY chase and update the entry's `dnssec_state` after the fact, or store an initial Unvalidated entry then let a background upgrade happen) before section-05 turns validation on for real traffic.

**MEDIUM — silent trust-anchor parse failure with no coverage for the reachable case.** `validate_for_store` (src/resolver/mod.rs:6229-6232) treats `TrustAnchors::from_u8` failure the same as "no anchors configured" and silently returns `Unvalidated` — no logging, no metric, nothing an operator could use to notice a misconfigured anchor file quietly disabled all DNSSEC validation. The only test exercising an unparseable anchor string (`resolve_forward_mode_never_invokes_dnssec_validator`) does so in Forward mode, which never reaches this branch — there is zero test proof of graceful degradation for the Recursive-mode parse-failure path specifically, and no negative-signal (log/metric) at all for what is a security-relevant silent failure mode.

**MEDIUM — growing already-strained positional argument lists papered over with `#[allow(clippy::too_many_arguments)]`** rather than a params struct. `build_rrset_entry`/`build_negative_entry`/`decompose_response_for_store` now carry `dnssec_ok: bool` and `store_authoritative: bool` as adjacent same-typed positional parameters plus a new `DnssecState`. A `CacheStoreOptions`-style struct would guard against a future transposition bug, but this matches the codebase's own established convention (`#[allow(clippy::too_many_arguments)]` is already used extensively elsewhere, e.g. every `ResolveQuery::with_cache*` constructor) — not a new smell introduced uniquely by this diff.

**LOW — missing an explicitly-listed §A6 test.** The plan calls for "A Secure entry's AD-bit behavior is unaffected by CD (no-regression check on `dnssec_ad_bit`...)" but the diff added no such test, and the existing candidate never varies `checking_disabled`.

**LOW — `validate_for_store` fetches its own fresh `self.backend.current()` snapshot** rather than reusing the `backend_snapshot`/`cache_epoch` already captured earlier by the caller. Under a backend hot-reload race the DS/DNSKEY chase could run against a different backend generation than the one that produced the response being validated. The doc comment asserts this is intentional/fine; no test covers a reload-during-validation race.

**LOW — `main.rs` wires `dnssec_validation_deadline` from `config.per_query_deadline`**, reusing a config value whose stated meaning (per the now-corrected doc comment) is actually appropriate once the HIGH finding above is resolved by documentation rather than redesign — see triage below.

Things that look correct and match the plan: Forward-mode-never-validates is proven with a real call-count spy; CD-independence of storage is proven end-to-end; the RRSIG-expiration TTL cap is correctly applied to both positive and negative entries; serve-stale Bogus-exclusion is correctly placed early in `stale_servability` with both a positive and a no-regression Secure test; the mixed-state CNAME chain test is a solid genuine multi-hop coverage addition; the single-verdict-per-response decision is a defensible, plan-sanctioned choice.
