# Code Review: Section 01 - DNSSEC Dependency and Feature Setup

Core mechanics match the plan: Cargo.toml adds `unstable-validator` and `ring` to the `domain` feature list, keeps the version floor at `0.12.1` (Cargo's caret semantics already bound this to <0.13.0, satisfying the plan's concern about silently crossing the 0.11->0.12 validator-API break), adds an explanatory comment next to the dependency line, and touches no `.rs` files — Cargo.lock resolves `domain` to 0.12.2 as the plan's 'Current state' section anticipated. Acceptance criteria 1, 2 (partially — see below), and 5 (no files other than Cargo.toml/Cargo.lock touched) are met.

**Main criticism:** the Cargo.toml comment ('Both transitively add moka and unstable-client-transport as new deps') materially undersells the actual supply-chain expansion, which the plan explicitly asked to be called out ('call that out explicitly in the PR description, not just as an inert dependency bump'). The Cargo.lock diff shows roughly 30 net-new packages, not two: moka pulls in async-lock, crossbeam-channel/epoch/utils, concurrent-queue, event-listener(-strategy), parking, parking_lot, portable-atomic, smallvec, tagptr, and uuid (which itself drags in js-sys/wasm-bindgen); ring pulls in cc, untrusted, a second getrandom (0.2.17 alongside the existing 0.4.3), and a second windows-sys (0.52.0 alongside 0.61.2) plus windows-targets and 7 per-arch windows_* crates; cc itself pulls find-msvc-tools and shlex. None of these are named or acknowledged anywhere.

A specific omission worth flagging to whoever reviews the PR: `ring` pulls in `cc`, a build-time dependency that shells out to a native C/assembly toolchain to build ring's optimized crypto primitives. The plan frames choosing `ring` over `openssl` as avoiding 'adding an OpenSSL system-dependency to the build' — that's true for linking, but the build still now requires a working C compiler in the environment, which is a similar-flavor supply-chain/build-environment risk that isn't mentioned.

Second gap: the diff also introduces duplicate dependency versions in the lock graph (windows-sys 0.52.0 and 0.61.2 side by side, getrandom 0.2.17 and 0.4.3 side by side) as a direct consequence of pulling in `ring`. Not blocking, but it's dependency-graph bloat that a careful review would flag and that isn't mentioned in the comment or PR description.

Third: the plan's Verification gates (cargo fmt --all -- --check, cargo clippy --all-targets, cargo test) and the Tests section's build/full-suite checks are the actual acceptance mechanism for this section. These were run manually during implementation (not visible to the subagent from the diff alone): `cargo build` succeeded, `cargo test` passed 701+28+39+8+1 tests with 0 failures (existing ignored network tests unchanged), `cargo fmt --all -- --check` and `cargo clippy --all-targets` both clean.

Nothing here blocks the dependency bump itself — the feature flags and version pin are correct — but the transparency requirement in the plan (Implementation step 3) is only partially satisfied: the comment names 2 of roughly 30 new transitive crates and omits the build-toolchain and dependency-duplication implications entirely.
